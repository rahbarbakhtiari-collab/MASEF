`docs/00-governance/WORDPRESS-PLUGIN-FACTORY-POLICY.md`

## هدف

تبدیل یک ایده کوتاه به افزونه‌ای فارسی، قابل‌تنظیم، امن، نگهداری‌پذیر، قابل‌نصب و آماده بررسی WordPress.org، بدون نیاز به مدیریت فنی مرحله‌به‌مرحله مالک محصول.

## حداقل سکوی فنی

- PHP: `8.1+`
- WordPress: `7.2+`
- پشتیبانی از نسخه‌های پایین‌تر لازم نیست.
- هدر افزونه، `readme.txt`، Composer، CI و مستندات باید همین حداقل‌ها را اعلام کنند.

## هویت ثابت

- Author: `رهبر بختیاری`
- License: `GPL-2.0-or-later`
- Slug: انگلیسی، کوتاه و ثابت
- Text Domain: دقیقاً برابر Slug
- Prefix و Namespace: انگلیسی، اختصاصی و بدون تداخل
- رابط محصول: فارسی و RTL
- مستندات عمومی WordPress.org: انگلیسی
- راهنمای کاربر: فارسی

## جریان محصول

1. ایده کوتاه دریافت می‌شود.
2. ChatGPT ایده را تحلیل، تکمیل و توسعه‌پذیر می‌کند.
3. خلاصه محصول شامل هدف، مخاطب، قابلیت‌ها، محدوده نسخه نخست، سطح خطر و معیارهای پذیرش یک‌بار تأیید می‌شود.
4. Codex همه مراحل فنی را بدون تأیید میانی اجرا می‌کند.
5. تحویل فقط پس از عبور از معیار آمادگی تحویل انجام می‌شود.

2. نیازمندی‌ها

## سیاست قابلیت‌ها

- قابلیت‌ها را به `essential`، `important` و `future` تقسیم کن.
- نسخه نخست همه قابلیت‌های ضروری و قابلیت‌های مهم کم‌خطر را شامل شود.
- قابلیت‌های آینده در Roadmap ثبت شوند.
- قابلیت لازم برای امنیت، داده، سازگاری یا جلوگیری از بازنویسی بزرگ را به نسخه نخست منتقل کن.
- از معماری توسعه‌پذیر استفاده کن، اما پیچیدگی فرضی و بی‌مصرف نساز.

## تنظیمات و پنل مدیریت

- هر رفتار محصولی که ممکن است میان سایت‌ها یا مدیران متفاوت باشد باید از پنل قابل تنظیم باشد.
- تنظیمات دارای پیش‌فرض کاربردی باشند تا افزونه بلافاصله قابل استفاده باشد.
- تنظیمات ضروری در صفحه اصلی و تنظیمات تخصصی در بخش «پیشرفته» قرار گیرند.
- جزئیات فنی داخلی وارد پنل نشوند.
- عملیات خطرناک هشدار و تأیید روشن داشته باشند.
- رابط مدیریت با الگوهای استاندارد WordPress هماهنگ، فارسی و RTL باشد.
- سازگاری LTR و ترجمه کامل حفظ شود.

## کنترل‌های فنی ثابت

- استفاده از WordPress API به‌جای SQL مستقیم، مگر با دلیل ثبت‌شده
- Capability و Nonce برای عملیات تغییردهنده
- Validation و Sanitization همه ورودی‌ها
- Escape خروجی در زمان نمایش
- `$wpdb->prepare()` برای SQL پویا
- جلوگیری از دسترسی مستقیم به فایل‌ها
- Prefix و Namespace اختصاصی
- Asset loading محدود به صفحه‌های لازم
- عدم بارگذاری مستقیم CDN
- عدم ذخیره Secret در کد یا مخزن
- کنترل AJAX، REST، Cron، Upload، Import/Export و نقش‌های کاربری در صورت وجود

## داده و چرخه عمر

- Activation فقط ساختار یا مقدار ضروری را ایجاد می‌کند.
- Deactivation هیچ داده‌ای را حذف نمی‌کند.
- Uninstall به‌طور پیش‌فرض داده‌ها را حفظ می‌کند.
- گزینه «حذف کامل تنظیمات و داده‌ها هنگام حذف افزونه» در پنل وجود دارد و پیش‌فرض آن خاموش است.
- حذف فقط داده‌های متعلق به همان افزونه را دربر می‌گیرد.
- Migration باید نسخه‌بندی‌شده، تکرارپذیر، قابل‌آزمون و امن برای داده موجود باشد.
- Upgrade نباید داده نسخه پیشین را از بین ببرد.

## حریم خصوصی و شبکه

- Telemetry و ردیابی به‌طور پیش‌فرض ممنوع است.
- ارتباط خارجی فقط برای قابلیت اصلی و با اطلاع روشن مدیر مجاز است.
- جمع‌آوری اختیاری داده پیش‌فرض خاموش است.
- نوع داده، مقصد، هدف و امکان غیرفعال‌سازی باید مستند شود.
- داده شخصی فقط به‌اندازه ضرورت ذخیره شود و در صورت نیاز Export/Erase پشتیبانی شود.

## وابستگی‌ها

- اولویت با WordPress Core API و PHP است.
- وابستگی تولیدی فقط با ارزش واقعی، مجوز مناسب، نگهداری فعال و امکان جایگزینی پذیرفته می‌شود.
- وابستگی توسعه‌ای برای تست، کیفیت و بسته‌بندی مجاز است، مشروط به اینکه وارد ZIP نهایی نشود مگر لازم باشد.
- هر وابستگی جدید از نظر امنیت، مجوز، اندازه و نگهداری بررسی می‌شود.

## آمادگی WordPress.org

- Header صحیح و هماهنگ

- کد خوانا و بدون Obfuscation
- بدون تبلیغ مزاحم، قفل مصنوعی یا وابستگی پنهان

- همه رشته‌های نمایشی ترجمه‌پذیر
- Privacy disclosure برای هر ارتباط خارجی
