# کنترل‌های کیفیت MASEF 0.3.1

MASEF همه مرحله‌های اصلی مهندسی را حفظ می‌کند. سطح پروژه فقط عمق کنترل، آزمون و شواهد را تغییر می‌دهد. کنترل کیفیت نباید به مجموعه‌ای از تأییدهای انسانی یا توقف‌های صوری تبدیل شود.

## اصل

> مراحل ثابت، عمق شناور، اجرای خودمختار، تأیید انسانی استثنایی.

## کنترل‌های ثابت

| کد | مرحله | مسئول اصلی | شرط عبور |
|---|---|---|---|
| Q1 | مسئله و نتیجه | ChatGPT + مالک محصول | نتیجه قابل‌مشاهده و مرز محصول روشن است |
| Q2 | نیازمندی‌ها | ChatGPT | نیازهای ضروری، مهم و آینده تفکیک شده‌اند |
| Q3 | معیارهای پذیرش | ChatGPT + Codex | معیارها مشخص، آزمون‌پذیر و قابل ردیابی‌اند |
| Q4 | طراحی فنی | Codex | معماری متناسب، امن، قابل نگهداری و قابل ارتقا است |
| Q5 | پیاده‌سازی | Codex | کد با طراحی و استانداردهای پروژه هماهنگ است |
| Q6 | آزمون | Codex + CI | آزمون‌های متناسب موفق‌اند و برای سبزشدن تضعیف نشده‌اند |
| Q7 | بازبینی | Codex یا بازبین مستقل | نقص مهم فنی، امنیتی، داده‌ای یا سازگاری باقی نمانده است |
| Q8 | بسته‌بندی | Codex | Artifact تمیز، نسخه‌بندی‌شده و قابل نصب است |
| Q9 | آمادگی استقرار | Codex | روش نصب، Upgrade، Rollback و محدودیت‌ها روشن‌اند |
| Q10 | بررسی پس از انتشار | Codex در محیط آزمایشی | نصب، فعال‌سازی و قابلیت اصلی در محیط معتبر بررسی شده است |

## تأیید خلاصه محصول

- مالک محصول فقط خلاصه محصول را یک‌بار تأیید می‌کند.
- Q1 تا Q3 می‌توانند در همان خلاصه محصول جمع شوند.
- پس از تأیید، Q4 تا Q10 بدون تأیید مرحله‌به‌مرحله توسط Codex اجرا می‌شوند.
- مالک محصول نباید میان ChatGPT و Codex پیام‌های فنی جابه‌جا کند.

## سطح سبک

همه Q1 تا Q10 اجرا می‌شوند، اما به‌شکل فشرده:

- نیازمندی و طراحی کوتاه
- تست مرتبط با هسته قابلیت
- بازبینی خودکار یا Self-review ثبت‌شده
- ZIP و Smoke Test
- گزارش نهایی مختصر

ADR، Threat Model رسمی، بازبین مستقل یا Evidence Pack مفصل فقط در صورت نیاز واقعی لازم‌اند.

## سطح استاندارد

همه Q1 تا Q10 با عمق معمول اجرا می‌شوند:

- نیازمندی و معیار پذیرش ثبت‌شده
- طراحی فنی کوتاه
- تست واحد، یکپارچگی و Smoke متناسب
- CI و بازبینی تغییرات
- آزمون Upgrade، Rollback و بسته نصب
- شواهد خلاصه تحویل

## سطح بحرانی

همه Q1 تا Q10 با کنترل عمیق اجرا می‌شوند:

- تصمیم‌های محصول و مالک خطر روشن
- Threat Model و طراحی امنیتی
- آزمون سوءاستفاده، نقش‌ها و دسترسی غیرمجاز
- آزمون Migration و بازیابی
- بازبینی مستقل در صورت ارزش واقعی
- شواهد کامل‌تر و نقطه توقف پیش از اقدام پرخطر Production

## معیار آمادگی تحویل افزونه WordPress

- معیارهای پذیرش اصلی موفق‌اند.
- نصب و فعال‌سازی بدون خطای جدی انجام می‌شود.
- Fatal Error، نقص امنیتی مهم یا خطر از دست‌رفتن داده وجود ندارد.
- قابلیت اصلی در WordPress واقعی یا محیط جایگزین معتبر آزموده شده است.
- Deactivation، Upgrade و Uninstall امن هستند.
- مستندات با نسخه ZIP هماهنگ‌اند.
- حداقل PHP `8.1` و نسخه پایدار دقیق WordPress ثبت‌شده در منشور پروژه، هدر، `readme.txt`، CI و آزمون‌ها به‌طور یکسان اعلام شده‌اند.
- نسخه Alpha، Beta یا RC جایگزین gate مسدودکننده نسخه پایدار نشده است.
- ZIP تمیز، SHA-256، Tag و Release آماده‌اند.
- ناسازگاری یا خطر مهم شناخته‌شده پنهان نشده است.

مقدار راستی‌آزمایی‌شده نمونه در ۲۰۲۶/۰۷/۲۸ WordPress `7.0.2` است؛ هر پروژه باید مقدار روز تصویب خود را از WordPress.org ثبت کند.

## قواعد توقف

توقف فقط وقتی مجاز است که یکی از این شرایط وجود داشته باشد:

- ابهام واقعی محصول با پیامد کسب‌وکاری متفاوت؛
- نیاز به Secret، ورود حساب یا مجوز انسانی؛
- هزینه یا خرید جدید؛
- حذف داده مهم یا اقدام برگشت‌ناپذیر؛
- پذیرش خطر امنیتی، حقوقی یا سازمانی؛
- استقرار پرخطر روی Production.

ناشناخته‌بودن جزئیات فنی، خرابی قابل‌تشخیص محیط یا شکست آزمون دلیل توقف نیست؛ Codex باید تا حد معقول تحلیل و اصلاح کند.
