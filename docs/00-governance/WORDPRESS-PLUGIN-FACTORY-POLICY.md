# سیاست ثابت کارخانه افزونه‌سازی وردپرس

> نسخه سیاست: 1.1  
> وضعیت: Active  
> دامنه: همه پروژه‌هایی که با پروفایل `wordpress-plugin` ساخته می‌شوند  
> تاریخ آخرین راستی‌آزمایی WordPress: 2026-07-28

## ۱. نقش‌ها و مدل همکاری

- مالک محصول ایده، هدف، محدودیت کسب‌وکار و نتیجه مطلوب را بیان می‌کند.
- ChatGPT نقش مدیر محصول و تحلیل‌گر را دارد: ایده را کامل، منطقی، توسعه‌پذیر و قابل‌آزمون می‌کند و یک خلاصه محصول برای تأیید ارائه می‌دهد.
- تأیید مالک محصول فقط یک‌بار و بر خلاصه محصول انجام می‌شود.
- پس از تأیید خلاصه، Codex رهبر فنی و مجری است و طراحی، پیاده‌سازی، آزمون، مستندسازی، GitHub و بسته‌بندی را بدون تأیید مرحله‌به‌مرحله انجام می‌دهد.
- مالک محصول مدیر فنی پروژه نیست و نباید پیام‌رسان میان ChatGPT و Codex شود. انتقال کار از طریق اسناد و وضعیت مخزن انجام می‌شود.

## ۲. چرخه مهندسی ثابت

هیچ پروژه‌ای مرحله‌های اصلی مهندسی را حذف نمی‌کند. تفاوت سطح‌ها فقط در عمق، شواهد و گستره آزمون است:

1. تعریف مسئله و نتیجه
2. نیازمندی‌ها
3. معیارهای پذیرش
4. طراحی فنی
5. پیاده‌سازی
6. آزمون
7. بازبینی
8. بسته‌بندی
9. آمادگی استقرار
10. بررسی پس از انتشار یا نصب آزمایشی

اصل اجرایی:

> مراحل ثابت، عمق شناور، اجرای خودمختار، تأیید انسانی استثنایی.

## ۳. سطح پروژه

Codex هر پروژه را مستقل در یکی از سطح‌های زیر طبقه‌بندی و در خلاصه محصول اعلام می‌کند:

- `light`: افزونه محدود، برگشت‌پذیر و بدون داده یا دسترسی حساس
- `standard`: افزونه چندماژولی، دارای داده معمولی، فرم، API یا اثر واقعی بر کاربران
- `critical`: پرداخت، اطلاعات حساس، احراز هویت، مهاجرت پیچیده، حذف گسترده یا پیامد جدی

این طبقه‌بندی نیازمند تأیید جداگانه نیست. همه مراحل مهندسی در هر سه سطح باقی می‌مانند.

## ۴. سیاست نسخه نخست و توسعه‌پذیری

- قابلیت‌ها به `essential`، `important` و `future` تقسیم می‌شوند.
- نسخه نخست شامل همه قابلیت‌های ضروری و قابلیت‌های مهم کم‌خطر است.
- قابلیت‌های باقی‌مانده در Roadmap ثبت می‌شوند.
- نسخه نخست باید «کامل‌ترین نسخه منطقی اول» باشد؛ نه نمونه ناقص و نه محصول بیش‌ازحد پیچیده.
- پروژه از ابتدا یک محصول زنده، نگهداری‌پذیر و نسخه‌بندی‌شده محسوب می‌شود.
- تغییر تنظیمات یا Schema باید Migration امن، حفظ داده موجود و مسیر Upgrade داشته باشد.
- هر نسخه دارای Changelog، ZIP مستقل، Tag و Release است.

## ۵. تنظیم‌پذیری محصول

- هر رفتار محصولی که میان سایت‌ها، مدیران، پروژه‌ها یا نیازهای کسب‌وکار قابل تغییر است باید از پنل افزونه قابل تنظیم باشد.
- جزئیات فنی داخلی مانند ساختار کلاس، روش Sanitization، Schema داخلی یا راهبرد Cache نباید بی‌دلیل وارد پنل شوند.
- همه تنظیمات دارای مقدار پیش‌فرض منطقی هستند تا افزونه پس از نصب قابل استفاده باشد.
- تنظیمات خطرناک یا نامفهوم فقط در صورت ضرورت و همراه با هشدار روشن ارائه می‌شوند.
- سازگاری Cache و زیرساخت تا حد ممکن خودکار است؛ فقط انتخاب‌های رفتاری واقعی به مدیر واگذار می‌شوند.

## ۶. خط مبنای فنی و کنترل نسخه WordPress

- حداقل PHP کارخانه: `8.1`.
- خط مبنای WordPress هر پروژه باید **آخرین نسخه پایدار رسمی** در زمان تصویب خلاصه محصول باشد و مقدار دقیق آن در منشور پروژه ثبت شود.
- مقدار راستی‌آزمایی‌شده فعلی در تاریخ 2026-07-28: WordPress `7.0.2`.
- WordPress `7.1` در تاریخ این سیاست پیش‌انتشار است و خط مبنای Production نیست.
- نسخه Alpha، Beta یا Release Candidate نباید به‌عنوان `Requires at least`، حداقل Production یا جایگزین آزمون نسخه پایدار استفاده شود.
- آزمون آینده‌نگرانه روی نسخه پیش‌انتشار فقط به‌صورت جداگانه و غیرمسدودکننده مجاز است.
- سازگاری با نسخه‌های پایین‌تر از خط مبنای ثبت‌شده پروژه هدف نیست.
- برای پشتیبانی از نسخه‌های قدیمی کد جایگزین، پیچیدگی یا مصالحه امنیتی ایجاد نمی‌شود.
- هدر افزونه، `readme.txt`، آزمون‌ها، CI، Issueها، PRها و مستندات باید مقدار دقیق و یکسانی اعلام کنند.
- افزایش خط مبنا فقط پس از انتشار رسمی نسخه پایدار و با این ترتیب انجام می‌شود:
  1. بررسی WordPress.org Release Archive و خبر رسمی انتشار؛
  2. اصلاح منشور، وضعیت و تصمیم پروژه؛
  3. اصلاح Issue و PR فعال؛
  4. اصلاح هدر، `readme.txt`، CI و آزمون‌ها؛
  5. اجرای آزمون واقعی و ثبت شواهد.
- حدس‌زدن شماره نسخه آینده یا ثبت نسخه منتشرنشده ممنوع است.

## ۷. زبان، ترجمه و رابط مدیریت

- زبان اصلی تجربه کاربری و پنل مدیریت فارسی و RTL است.
- همه متن‌ها ترجمه‌پذیر و دارای Text Domain هستند.
- Slug و Text Domain دقیقاً یکسان، انگلیسی، کوتاه و ثابت‌اند.
- فایل الگوی ترجمه تولید می‌شود و ظاهر LTR نباید شکسته باشد.
- پنل مدیریت ساده، هماهنگ با رابط WordPress و دارای دسته‌بندی روشن است.
- تنظیمات اصلی در دسترس و تنظیمات تخصصی در بخش «پیشرفته» قرار می‌گیرند.
- هر گزینه عنوان روشن، توضیح کوتاه و مقدار پیش‌فرض کاربردی دارد.

## ۸. داده، غیرفعال‌سازی و حذف

- غیرفعال‌سازی هیچ تنظیم یا داده‌ای را حذف نمی‌کند.
- حذف افزونه نیز به‌طور پیش‌فرض داده‌ها را حفظ می‌کند.
- پنل افزونه دارای گزینه «حذف کامل تنظیمات و داده‌ها هنگام حذف افزونه» است که پیش‌فرض آن خاموش است.
- در صورت فعال‌بودن این گزینه، Uninstall فقط داده‌های متعلق به همان افزونه را با کنترل امنیتی حذف می‌کند.
- داده‌های مشترک، نوشته‌های عادی WordPress یا داده افزونه‌های دیگر هرگز حذف نمی‌شوند.
- عملیات حذف حساس باید هشدار واضح داشته باشد.
- Migration، Upgrade و سازگاری داده میان نسخه‌ها باید امن و آزموده باشند.

## ۹. وابستگی‌ها و ارتباط خارجی

- اولویت با APIهای اصلی WordPress و امکانات PHP است.
- وابستگی خارجی فقط با فایده واقعی، مجوز مناسب، نگهداری فعال و امکان جایگزینی پذیرفته می‌شود.
- فایل JavaScript، CSS یا فونت نباید مستقیماً از CDN عمومی بارگذاری شود.
- Secret، Token، کلید API و رمز هرگز داخل کد یا مخزن قرار نمی‌گیرند.
- سرویس خارجی فقط وقتی مجاز است که برای قابلیت اصلی لازم باشد و رفتار آن در پنل و مستندات روشن باشد.

## ۱۰. حریم خصوصی

- Telemetry، ردیابی و ارسال آمار استفاده به‌طور پیش‌فرض ممنوع است.
- افزونه بدون رضایت روشن مدیر نباید اطلاعات سایت یا کاربر را به بیرون ارسال کند.
- هر ارتباط خارجی باید هدف، نوع داده، مقصد و امکان غیرفعال‌سازی روشن داشته باشد.
- جمع‌آوری اختیاری داده پیش‌فرض خاموش است.
- داده شخصی فقط به‌اندازه ضرورت ذخیره می‌شود و در صورت کاربرد، حذف و Export آن پشتیبانی می‌شود.

## ۱۱. امنیت

امنیت در همه پروژه‌ها یک مرحله ثابت است. حداقل کنترل‌ها:

- Capability و کنترل سطح دسترسی
- Nonce برای عملیات تغییردهنده
- Validation و Sanitization ورودی‌ها
- Escape خروجی در زمان نمایش
- Query امن و استفاده از `$wpdb->prepare()`
- جلوگیری از دسترسی مستقیم به فایل‌ها
- کنترل Admin، AJAX، REST، Cron و Upload در صورت وجود
- جلوگیری از افشای Secret و اطلاعات حساس
- آزمون دسترسی غیرمجاز و نقش‌های کاربری
- ثبت خلاصه بررسی امنیتی

در سطح `critical` آزمون سوءاستفاده و شواهد امنیتی عمیق‌تر لازم است. توقف انسانی فقط برای پذیرش آگاهانه یک خطر واقعی امنیتی مجاز است.

## ۱۲. آمادگی WordPress.org

از نسخه نخست:

- مجوز `GPL-2.0-or-later` یا مجوز GPL-compatible معتبر؛
- نام نویسنده `رهبر بختیاری`؛
- Slug، Text Domain و نام پوشه اصلی یکسان؛
- `readme.txt` استاندارد و انگلیسی؛
- همه رشته‌های نمایشی ترجمه‌پذیر؛
- کد خوانا و بدون Obfuscation؛
- ZIP تمیز و بدون فایل توسعه یا Secret؛
- Privacy disclosure برای هر ارتباط خارجی؛
- Changelog، Upgrade notice و مستندات هماهنگ.

## ۱۳. آزمون و محیط اجرا

- ابتدا LocalWP موجود استفاده و مشکل آن به‌طور معقول تشخیص و تعمیر می‌شود.
- در صورت نامناسب‌بودن LocalWP، Docker و محیط مستقل WordPress استفاده می‌شود.
- خرابی محیط پروژه را متوقف نمی‌کند؛ پس از تلاش معقول، آزمون جایگزین قوی و محدودیت دقیق ثبت می‌شود.
- آزمون نصب ZIP روی WordPress واقعی الزامی است، مگر ناممکن‌بودن واقعی و مستند.
- نصب، فعال‌سازی، قابلیت اصلی، دسترسی، Upgrade، Deactivation، Uninstall، RTL/LTR و ZIP آزموده می‌شوند.
- خط مبنای پایدار ثبت‌شده پروژه باید یک gate مسدودکننده CI باشد.

## ۱۴. Git و GitHub

- هر افزونه مخزن مستقل دارد.
- مخزن ابتدا Private ساخته می‌شود و پس از آمادگی انتشار Public می‌شود.
- Commit و Push فقط در واحدهای کاری معنادار انجام می‌شوند.
- `main` همیشه سالم و آزموده است.
- Pull Request فقط وقتی ارزش واقعی برای CI، بازبینی یا تغییر مهم دارد استفاده می‌شود.
- هر نسخه تحویلی Tag، Release، Changelog و ZIP مستقل دارد.

## ۱۵. معیار آمادگی تحویل

- معیارهای پذیرش اصلی موفق‌اند.
- نصب و فعال‌سازی بدون خطای جدی انجام می‌شود.
- Fatal Error، نقص امنیتی مهم یا خطر ازدست‌رفتن داده وجود ندارد.
- قابلیت اصلی در WordPress واقعی یا محیط جایگزین معتبر آزموده می‌شود.
- غیرفعال‌سازی، Upgrade و Uninstall امن‌اند.
- مستندات با نسخه تحویلی هماهنگ‌اند.
- ناسازگاری یا محدودیت مهم پنهان نشده است.

## ۱۷. مرز استقرار

- نصب نهایی Production و تغییر داده واقعی Production بر عهده مالک محصول است.
- اقدام پرخطر Production، هزینه، Secret، حذف برگشت‌ناپذیر یا پذیرش خطر مهم نیازمند توقف انسانی است.
